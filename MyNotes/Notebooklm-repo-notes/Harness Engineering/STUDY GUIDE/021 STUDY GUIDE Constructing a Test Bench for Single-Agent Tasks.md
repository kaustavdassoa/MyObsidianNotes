# 📚 STUDY GUIDE: Constructing a Test Bench for Single-Agent Tasks

## 1. Concise Overview of the Topic

In the field of Agentic AI, evaluating an autonomous agent requires more than just checking its final text output. As agents begin to execute code, retrieve data, and interact with operating systems, developers must build dedicated **evaluation harnesses**—also known as test benches. Constructing a test bench for a single-agent task involves creating a secure, sandboxed environment, instrumenting the agent's execution to capture a complete log of its actions, and implementing automated scoring systems to verify both the accuracy and safety of its behavior. At the intermediate level, mastering harness engineering means understanding how to decouple the agent from the evaluator, safely grade unpredictable (stochastic) outputs, and move beyond binary "Pass/Fail" metrics.

---

## 2. Key Concepts & Definitions

- **The Evaluation Interface (V-Component):** The specific part of the agent execution harness responsible for instrumenting the execution to capture action trajectories, intermediate states, and success signals for automated analysis.
- **Stochastic Test Semantics:** The principle that agent testing must shift from deterministic, binary verdicts (Pass/Fail) to probabilistic, three-valued verdicts (Pass, Fail, Inconclusive) because the same agent prompt and tools can yield different execution paths across multiple runs.
- **Agent-Evaluator Isolation:** A mandatory design principle ensuring that the system under test (the agent) cannot read, write, or influence the environment where the evaluation (grading) takes place.
- **The Log "Sandwich":** A conceptual model for tracing an agent's execution. It consists of the inputs (task instructions, system prompts), the execution loop (reasoning chains, tool calls, environment errors), and the outputs (final submission, grader outcome).
- **LLM-as-a-Judge:** Using a secondary, highly capable language model to evaluate the subjective qualities or complex outputs of an agent, provided the inputs to the judge are sanitized against prompt injections.

---

## 3. Important Details: How to Build a Functional Test Bench

Building a functional test bench for a specific, constrained task (like code execution or data retrieval) requires coordinating several infrastructure layers.

### A. Environment Setup & Isolation

If an agent can see the expected answer or manipulate the grading script, the benchmark measures lookup speed or exploitation rather than capability.

- **Remote Sandboxing:** Execute the agent's actions inside an isolated environment, such as a Docker container.
- **Separate the Evaluator:** Extract the raw artifacts (logs, generated files) through a controlled channel and run the evaluation script on a completely separate, read-only host.
- **Hide the Gold Answers:** Task configurations exposed to the agent should only contain what a human would know; evaluation metadata and expected answers must live on an inaccessible path.

### B. Capturing the Execution Trace (Logging)

Because agents can achieve a correct outcome through dangerous or flawed intermediate steps (a "lucky pass"), the test bench must record the process.

- Implement deep telemetry to capture the entire "log sandwich".
- Record token usage, reasoning chains, tool invocations, shell outputs, and any errors generated by the environment.
- This structured tracing is mandatory for determining whether an agent followed safe, logical steps to retrieve data or execute code.

### C. Automated Scoring for Accuracy and Safety

A robust test bench uses a combination of grading techniques:

- **Rule-Based Evaluation (Deterministic Sensors):** For code execution or data retrieval tasks with verifiable ground truths, translate rubrics directly into assertion logic within an evaluation script. Use compilers, linters, and test suites as deterministic sensors.
- **LLM-Based Evaluation:** For subjective deliverables, use an LLM-as-a-judge. However, you must treat the agent's output as untrusted input: strip content resembling system prompts, and use structural markers to tell the judge to treat the agent's output purely as data to avoid prompt injection attacks against the evaluator.
- **Safety Verification:** To evaluate safety, integrate formal property checkers (like Linear Temporal Logic templates) or specific compliance scripts to automatically flag if an agent attempted to delete files, access forbidden domains, or leak credentials during its trace.

### D. Statistical Aggregation

Because agents are stochastic, a single test run is insufficient.

- Run the same task multiple times (e.g., $k$ times).
- Use metrics like **pass@k** (probability of passing at least one of $k$ runs) to measure raw capability, and **pass^k** (probability of passing all $k$ runs) to measure consistency and reliability.

## 7. Practice Questions with Answers

**Q1: Why is it dangerous to run an agent and its evaluation script in the exact same Docker container?** _Answer:_ If there is no isolation between the agent and the evaluator, an agent can write state to the shared environment, tamper with the evaluation data, or overwrite the grading script to artificially assign itself a perfect score.

**Q2: What is the difference between Rule-Based Evaluation and LLM-as-a-Judge in an automated test bench?** _Answer:_ Rule-based evaluation relies on deterministic assertions (like executing a unit test or checking an Abstract Syntax Tree) to verify objective ground truths. LLM-as-a-judge is used for subjective or complex tasks (like assessing UI layout or code readability) by prompting a secondary model with a rubric to score the output.

**Q3: When constructing a test bench, why must the grading system incorporate a "Log Sandwich" instead of just evaluating the final output?** _Answer:_ Because checking only the final outcome can mask "lucky passes" (where an agent hallucinates but guesses right) or dangerous intermediate steps. The log sandwich captures the inputs, execution loop (tool calls, reasoning), and outputs, allowing the test bench to evaluate the safety and logic of the agent's process.

**Q4: How does a test bench deal with the fact that AI agents are stochastic (non-deterministic)?** _Answer:_ A test bench must use stochastic test semantics, running the agent multiple times on the same task. It replaces binary Pass/Fail verdicts with a three-valued system (Pass, Fail, Inconclusive) and utilizes metrics like pass@k and pass^k to measure consistency across runs.

## 8. Key Takeaways & Exam-Style Points

- **Outcome vs. Process:** Never build a test bench that only checks the final deliverable. You must instrument the environment to score the _trajectory_ (process).
- **The Baseline for Safety:** Evaluating safety in a test bench requires observing intermediate tool calls. An agent that successfully retrieves data but attempts to delete a database along the way has failed the safety evaluation, even if the final data is correct.
- **Adversarial Evaluator Testing:** Before finalizing a test bench, you should run a "null agent" (does nothing) and a "state-tampering agent" (tries to hack the system) against it. If they score above zero, the test bench is broken.
- **V-Component Isolation:** The Evaluation Interface ($V$) must be decoupled from the Execution Loop ($E$) and Action Interface ($I_{act}$) to maintain benchmark integrity.
