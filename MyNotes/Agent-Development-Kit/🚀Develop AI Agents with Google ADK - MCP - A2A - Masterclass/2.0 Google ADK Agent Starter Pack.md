# Google ADK: Agent Starter Pack 

## 1. What is the Agent Starter Pack?

The **Agent Starter Pack** (often referred to as the Agent Starter Kit) is the official CLI-driven scaffolding and deployment toolset within the Google Agent Development Kit (ADK) ecosystem. 

While the core ADK helps you write the internal logic of your agent (prompts, tools, and routing), the Starter Pack solves the **"Day 2" operational challenges**. It acts as the critical bridge between running a script on your laptop and deploying an enterprise-grade service. By providing pre-configured MLOps pipelines, CI/CD workflows, evaluation harnesses, and infrastructure-as-code (IaC) templates, it ensures developers can focus entirely on agent intelligence without getting bogged down by deployment boilerplate.

> [!tip] The Enterprise Edge
> In secure production environments one cannot simply deploy a Python script to a server. The Starter Pack ensures agents are immediately wrapped in secure, observable, and scalable deployment architectures tailored for Google Cloud.

---

## 2. Core Commands & Workflows: `create` vs. `enhance`

The Starter Pack CLI operates primarily through two distinct workflows, depending on the lifecycle stage of your project:

### The `create` Workflow
Use this when starting a brand new project. The `create` command scaffolds an entirely new repository from scratch. It generates the directory structure, the base agent logic, the deployment templates, and the evaluation harnesses all at once. It is the fastest way to go from zero to a production-ready repository.

### The `enhance` Workflow
Use this when you have already built a barebones ADK agent locally and now want to make it production-ready. The `enhance` command inspects your existing directory and carefully injects the missing MLOps, CI/CD, and deployment boilerplate around your custom logic without overwriting your core agent code.

> [!tip] Dependency Management
> The Agent Starter Pack heavily utilizes `uv` (an ultra-fast Python package installer and resolver). Ensure `uv` installed in the environment before running these commands, as it handles the creation of isolated virtual environments for your agent templates.

## 3. Configuration Options & Flags

Below is a breakdown of the primary flags used to customize how the Starter Pack generates your project.

| Option / Flag               | Specific Usage                                                                                                                                  | Command Example                                         |
| :-------------------------- | :---------------------------------------------------------------------------------------------------------------------------------------------- | :------------------------------------------------------ |
| `-a`, `--agent-source`      | Defines the source code or template to use as the foundation for the agent. Can be a default template, a GitHub URL, or a local directory path. | `uvx agent-starter-pack create -a google/default-agent` |
| `-d`, `--deployment-target` | Specifies the intended production infrastructure environment. This dictates which IaC and CI/CD files are generated.                            | `uvx agent-starter-pack create -d agent_engine`         |
| `-n`, `--project-name`      | Explicitly sets the name of the generated folder and the project variables inside the scaffolded files.                                         | `uvx agent-starter-pack create -n compliance-bot`       |
| `--dry-run`                 | Simulates the scaffolding process and lists the files that *would* be created or modified, without actually writing to disk.                    | `uvx agent-starter-pack enhance --dry-run`              |

## 4. Detailed CLI Examples

Here are the specific `uvx agent-starter-pack` commands for standard development scenarios:

### Creating a new agent using the default ADK base template
This is the standard starting point, providing a basic, well-structured agent ready for customization.

```bash
uvx agent-starter-pack create -n my-default-agent
```


### Creating an agent using a specific GitHub repository

One can leverage an approved "golden template" stored in GitHub which can be used as a scaffold directly from it.

```bash
uvx agent-starter-pack create -a https://github.com/my-org/agent-goldent-template -n agent-name
```

### Creating an agent using a local directory as the source

Ideal for testing local templates or duplicating a baseline agent stored elsewhere on your machine.

```bash
uvx agent-starter-pack create -a /path/to/local/reference/agent -n new-local-agent
```

### Deploying targeting Vertex AI Agent Engine

This command scaffolds the project specifically for deployment to Google Cloud's Vertex AI Agent Engine, generating the correct deployment YAMLs and required Google Cloud build steps.

```bash
uvx agent-starter-pack create -d agent_engine -n vertex-ready-agent
```

### Enhancing an existing barebones directory

Inject production-ready templates (like CI/CD pipelines and deployment configs) into a local agent you've already built, targeting a secure Cloud Run deployment.

```bash
cd existing-agent-dir
uvx agent-starter-pack enhance -d cloud_run
```

> [!warning] Verify Enhancements 
> 
> Always use `git status` or run the `--dry-run` flag before using the `enhance` command on an existing repository to ensure you understand exactly which configuration files are being added or modified.


### Google ADK: Resume Optimizer Deployment Guide

#### 1. Deployment Architecture & Security Context

Deploying an agent requires transitioning from a local `adk api_server` to a secure, production-ready environment like Google Cloud Run. 

This ensures LLM provider (e.g., Vertex AI) is configured with a zero-data-retention policy so that no user data is not inadvertently used for model training. The Cloud Run service should be stateless, dropping all user context the moment the session concludes.

#### 2. Preparing the Agent (`enhance` Workflow)

Assuming the core agent logic (prompts, LangGraph routing, and tool calling) is already built in a local directory, the Agent Starter Pack can inject the necessary deployment boilerplate without overwriting your custom logic.

Navigate to the existing agent directory and run the `enhance` command targeting Cloud Run:

```bash
cd /path/to/existing-agent-dir
## This command will generate the required Dockerfile, cloudbuild.yaml, and infrastructure-as-code files tailored for a secure Cloud Run deployment.
uvx agent-starter-pack enhance -d cloud_run
```

#### 3. Environment Variables & Secret Management

An existing agent is likely relies on an LLM backend (like Vertex AI or Gemini). Authentication credentials should never be hardcoded into the agent's code or the Dockerfile.

>[!tip] Securing API Key
>Store any necessary API keys or service account credentials in Google Cloud Secret Manager. Grant the Cloud Run service account the Secret Manager Secret Accessor role. Expose these secrets to the agent at runtime as environment variables.

> [!info] Vertex AI Default Credentials
If you are deploying on Google Cloud and using Vertex AI, you often don't need explicit API keys. The ADK can leverage Application Default Credentials (ADC) tied directly to the Cloud Run instance's service account.

#### 4. Deployment Steps (Cloud Run)
Once the directory is enhanced and secrets are configured, one can seamlessly build and deploy the container.

**Step A: Build the Container Image**
Using Google Cloud Build, package the Resume Optimizer agent into a secure container:

```bash
gcloud builds submit --tag gcr.io/YOUR_PROJECT_ID/agent-name-service
```

**Step B: Deploy Securely**

Deploy the newly built image to Cloud Run. Crucially, the --no-allow-unauthenticated flag is used to lock down the endpoint, ensuring only IAM-authorized users or services can submit resumes for optimization.

```bash
gcloud run deploy agent-name-service \
  --image gcr.io/YOUR_PROJECT_ID/agent-name-service \
  --region asia-south1 \
  --no-allow-unauthenticated \
  --service-account agent-sa@YOUR_PROJECT_ID.iam.gserviceaccount.com
```

>[!info] Region Selection
Deploying to asia-south1 (Mumbai) or a geographically appropriate region ensures lower latency and can help satisfy data residency requirements when processing local candidate data.

#### 5. Invoking the Deployed Optimizer
To test the live agent, one must pass an OIDC identity token.

```bash
export AGENT_URL=$(gcloud run services describe resume-optimizer-service --region asia-south1 --format 'value(status.url)')/run

curl -X POST $AGENT_URL \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $(gcloud auth print-identity-token)" \
  -d '{
    "app_name": "Calling_App_Name",
    "new_message": "User Message goes here",
    "user_id": "<user-id-for-tracking>",
    "session_id": "<user-session-id-session-management>"
  }'
  ```
