# Google ADK Overview

This note provides an overview of the Google Agent Development Kit (ADK), highlighting its key features, benefits, and supporting platforms for developing AI-powered agents.

## Available Frameworks in the Market
Here's a list of prominent frameworks available for building AI agents:
- Crew AI
- Agent Lite
- LangChain / LangGraph
- Microsoft AutoGen
- AgentFlow
- Google ADK

## Key Benefits of using Google ADK
Google ADK offers several advantages for developers:
- Seamlessly integrates with the set of tools provided by Google to help developers build AI-Powered Agents.
- Tools, Functions, and API Integration
- Multi-Step Reasoning
- Session, Memory, and Context Handling
- Easy Development in Google Cloud
- Multi-model support
- Open Source
- Integration with other Agentic Frameworks
- Sequential and/or parallel execution.

## Google ADK Important CLI Commands

| Command          | Description                                                                                                                                                                                         | Best For                                                                | Not Recommended For                                                 |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------- |
| `adk web`        | Launches the ADK Web UI, a browser-based chat interface for your agents. This provides a user-friendly graphical interface to interact with and test your AI agents directly from your web browser. | Quick UI testing, interactive demos, user-friendly exploration.         | Production deployments, heavy automation, server-side tasks.        |
| `adk run`        | Used to run an interactive command-line interface (CLI) for a specified agent. | `adk create`     | Initializes a new agent application with a pre-defined template.                                                                                                                                    | Starting new agent projects quickly, scaffolding basic agent structure. | Modifying existing complex projects, advanced customization.        |
| `adk api_server` | Starts a FastAPI server that exposes your agent as a REST API, enabling integration with other applications or services.                                                                            | Integrating agents into other applications, building microservices.     | Direct user interaction, standalone CLI tools, simple scripts.      |
| `adk deploy`     | Facilitates the deployment of your agent to cloud platforms like Cloud Run or GKE.                                                                                                                  | Deploying agents to cloud infrastructure for production use.            | Local development, quick testing, ad-hoc script execution.          |
| `adk eval`       | Used for evaluating agent performance using predefined evaluation sets.                                                                                                                             | Measuring agent performance, quality assurance, regression testing.     | Development/runtime, creating new agents, interactive use.          |

# Agent Invocation Example 

This section outlines the API invocation patterns for a simple Google Agent Development Kit (ADK) "**Weather Agent**". It covers both the local development workflow and the secure, IAM-backed cloud deployment model.

#### 1. Local Invocation (`adk api_server`)
During local development, the ADK exposes a straightforward REST endpoint to interact with your agent. By default, running `adk api_server` spins up a local server on port 8000.

```bash
curl -X POST http://localhost:8000/run \
  -H "Content-Type: application/json" \
  -d '{
    "app_name": "weather_agent",
    "new_message": "What is the weather like in Bengaluru today?",
    "user_id": "dev_user_01",
    "session_id": "session_alpha_123"
  }'
```

> [!info] 
>The Importance of Optional Fields for Agentic Memory While `user_id` and `session_id` are technically optional for a single stateless request, they are the backbone of agentic memory. Providing a consistent `session_id` allows the ADK's underlying state management (like Checkpointer in LangGraph) to retrieve the conversation history. Without these fields, the Weather Agent will suffer from "amnesia" on every call, losing the context of previous follow-up questions (e.g., asking "What about tomorrow?" immediately after asking for today's weather).

#### 2. Cloud Invocation (Cloud Run + IAM Security)
When moving a multi-agent AI platform into a cloud environment — a strict zero-trust architecture must be enforced. Deploying the ADK to Google Cloud Run with the **"Require Authentication"** flag ensures that the endpoint is shielded from the public internet.

Every request must be authenticated using Google Cloud IAM. Callers must present a valid OpenID Connect (OIDC) identity token to prove they have the `roles/run.invoker` permission.

To call the secure Cloud Run endpoint, one must dynamically generate and inject a Bearer token into the Authorization header.

```bash
# Set your Cloud Run URL
export AGENT_URL="https://weather-agent-service-xyz123-uc.a.run.app/run"

# Invoke the endpoint with an OIDC Identity Token
curl -X POST $AGENT_URL \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $(gcloud auth print-identity-token)" \
  -d '{
    "app_name": "weather_agent",
    "new_message": "Is it raining in London?",
    "user_id": "service_account_prod_01",
    "session_id": "compliance_audit_thread_99"
  }'
```

>[!tip] Session State Persistence (Local vs. Cloud) 
>When testing locally, `adk api_server` often defaults to an in-memory SQLite database for session state. When deploying to Cloud Run, instances are stateless and ephemeral. You must configure your ADK deployment to use an external persistent storage backend (like Cloud SQL or Firestore) for memory; otherwise, passing the `session_id` in production will not successfully retrieve past context.
