## Core Concepts

> [!info] Model Context Protocol (MCP)
> An open standard introduced by **Anthropic** acting as a **"USB-C port for AI."** It provides a universal, secure architecture to connect AI models to external datasets, APIs, and local files, eliminating the need for custom, one-off integrations.

* **MCP Server:** A lightweight backend application that securely **exposes** specific data, files, or capabilities to an AI.
* **MCP Client:** The host application (e.g., Claude Desktop, Cursor IDE) that manages the networking connection to the server and **consumes** the tools.

> [!info] MCP Client vs. AI Agent
> * **Raw MCP Client:** Purely infrastructural networking protocol. Requires exact function names and properly formatted JSON arguments. Has zero autonomy and outputs raw strings/data directly from the server.
> * **AI Agent:** Wraps the MCP client with an **LLM "brain."** Accepts natural language, autonomously decides if/when to use available tools, and synthesizes raw data into a conversational answer.

### MCP Primitives
Server capabilities are exposed using specific decorators based on desired AI interaction:
* **`@mcp.tool()`:** Executable functions that take arguments and return results (e.g., querying a DB). Use when the AI needs to *take action*.
* **`@mcp.resource()`:** Read-only static data exposed via a URI (e.g., `file:///logs`). Use to provide context *without* requiring the AI to pass arguments.
* **`@mcp.prompt()`:** Reusable prompt templates provided by the server to standardize user-AI interactions for specific localized tasks.

## Technical Implementation

##### **The MCP Server (`server.py`)**
Uses `FastMCP` to expose a hardcoded employee database as an executable tool. This server hardcodes an employee database and exposes a tool to fetch an employee by ID.

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("Employee Directory Server")

EMPLOYEES = {
    "101": {"name": "Alice Smith", "role": "Lead Engineer", "department": "IT"},
    "102": {"name": "Bob Jones", "role": "HR Manager", "department": "HR"}
}

@mcp.tool()
def get_employee_details(emp_id: str) -> str:
    """Fetch employee details using their employee ID."""
    employee = EMPLOYEES.get(emp_id)
    if employee:
        return f"Name: {employee['name']}, Role: {employee['role']}, Dept: {employee['department']}"
    return f"Error: No employee found with ID {emp_id}"

if __name__ == "__main__":
    mcp.run()
```

##### **The MCP Client (`client.py`)**
A raw client simply handles the networking. It does **not** use an LLM. It just connects to the server and executes the tool deterministically.

```python
import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client

async def run_client():
    server_params = StdioServerParameters(command="python", args=["server.py"])

    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            result = await session.call_tool("get_employee_details", arguments={"emp_id": "101"})
            print(f"Server Response: {result.content[0].text}")

if __name__ == "__main__":
    asyncio.run(run_client())
```

##### **AI Agent (`agent.py`- Conceptual) 
Combines an MCP Client with an LLM SDK to autonomously select and execute tools based on natural language queries.

```python 
import asyncio
from mcp import ClientSession, StdioServerParameters
from mcp.client.stdio import stdio_client
# import your_favorite_llm_sdk as llm

async def run_agent(user_query: str):
    server_params = StdioServerParameters(command="python", args=["server.py"])

    async with stdio_client(server_params) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            available_tools = await session.list_tools()
            
            # 1. LLM Routing Step (Conceptual)
            # llm_decision = llm.plan(user_query, available_tools) -> Chooses 'get_employee_details' with '102'
            
            # 2. Agent Execution
            tool_result = await session.call_tool("get_employee_details", arguments={"emp_id": "102"})
            
            # 3. LLM Synthesis Step (Conceptual)
            # final_answer = llm.synthesize(tool_result.content[0].text, user_query)
            print("Agent: Based on the system, Bob Jones is the HR Manager.")

if __name__ == "__main__":
```

#### What is the difference between a Client and an Agent?

| **Feature**      | **Raw MCP Client**                                                   | **AI Agent (using MCP Client)**                                                |
| ---------------- | -------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **Intelligence** | None. It is purely infrastructural (networking protocol).            | High. Uses an LLM to reason, plan, and understand language.                    |
| **Input**        | Requires exact function names and properly formatted JSON arguments. | Accepts vague, natural language goals (e.g., "Find Bob's role").               |
| **Autonomy**     | Zero. It only executes what you hardcode it to execute.              | High. It inspects available tools and _chooses_ if/when to use them.           |
| **Output**       | Raw JSON/String data directly from the server.                       | A conversational, synthesized answer combining the data with natural language. |
**In short:** The **Client** is the telephone line connecting to the server. The **Agent** is the person picking up the phone, deciding who to call, and explaining the conversation to you afterward.

### **Understanding `@mcp.tool`, `@mcp.resource`, and `@mcp.prompt`**

MCP categorizes capabilities into three main primitives. You use specific decorators in your server code depending on what you want the AI to do.

#### **1. `@mcp.tool()`**

- **What it is:** Executable functions. They take arguments, perform actions, and return results.
- **When to use it:** When the AI needs to _do_ something, compute something, or search for something specific based on user input.
- _Examples:_ Searching a database, fetching a live weather API, running a bash script, or the `get_employee_details(emp_id)` function above.

#### **2. `@mcp.resource()`**

- **What it is:** Read-only data. It exposes data through a URI (like `file:///app/logs` or `postgres://schema`).
- **When to use it:** When you want to provide context or static data to the AI _without_ requiring the AI to pass arguments. It's like handing the AI a document to read before it starts working.
- _Examples:_ Exposing an API documentation file, a system architecture diagram, or a database schema.

#### **3. `@mcp.prompt()`**

- **What it is:** Reusable prompt templates provided by the server.
- **When to use it:** When you want to standardize how users interact with the AI for specific tasks related to your server.
- _Examples:_ A "Code Review Prompt" that automatically asks the AI to evaluate code against your company's specific style guide, pulling in a `resource` as context.

To understand how `@mcp.resource()` handles complex, dynamic data like live logs, we first need to correct a common misconception about how Large Language Models work: **LLMs do not have continuous, real-time "live streams" of data flowing into their brains.** An LLM's context window is a static snapshot taken at the exact moment you hit "send."

Because of this, the Model Context Protocol (MCP) doesn't literally stream an open TCP socket of infinite logs directly into the neural network. Instead, it uses a highly structured combination of **URI Templates**, **Standardized JSON payloads**, and a **Publish/Subscribe (Pub/Sub) notification system** to create the _effect_ of a live stream.

Here is the exact breakdown of how it works under the hood.

### 1. The URI Architecture and Templates

When you expose a resource in an MCP server, you assign it a custom URI. For dynamic data like logs, you typically use **Resource Templates**, which allow the client to request specific slices of data rather than the whole server.

Python

```
# The server defines a template that accepts variables
@mcp.resource("logs://{environment}/{service_name}")
def get_service_logs(environment: str, service_name: str) -> str:
    """Fetch the latest logs for a specific service."""
    # Logic to fetch the last 100 lines of the requested log
    return tail_logs(environment, service_name, lines=100)
```

### 2. The Data Formatting (JSON-RPC)

When the MCP Client (like your IDE or chat app) requests that resource, the MCP Server doesn't just return raw text. It wraps the data in a strict JSON-RPC format defined by the MCP specification.

It handles two primary formats: `text` and `blob` (binary).

JSON

```
// Example of the Server's response to the Client
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "contents": [
      {
        "uri": "logs://production/auth-service",
        "mimeType": "text/plain",
        "text": "[2026-03-22 08:14:00] INFO: User 405 authenticated.\n[2026-03-22 08:14:02] WARN: Latency spike detected."
      }
    ]
  }
}
```

_Note: If this were an image or a compiled binary file, the `mimeType` would change, and the payload would use the `blob` field with a Base64 encoded string instead of `text`._

### 3. The "Streaming" Mechanism: Pub/Sub Notifications

Since the context window is static, how does the AI know when new logs appear? It uses MCP's notification system.

1. **Subscribe:** When the AI agent decides it needs to monitor a log, the MCP Client sends a `resources/subscribe` request for `logs://production/auth-service`.
    
2. **Listen:** The MCP Server keeps track of this subscription.
    
3. **Notify:** When a new error pops up in the actual log file, the MCP Server fires a one-way notification back to the client: `notifications/resources/updated`.
    
4. **Context Update:** The MCP Client receives this ping. It then automatically re-fetches the resource and silently updates the text within the LLM's active context window (or system prompt) so that the _next_ time the LLM generates a token, it has the absolute latest data.
    

### 4. Protecting the Context Window

Live logs can be massive. If an MCP server naively dumped a 500MB log file into the `text` field, it would instantly blow out the LLM's context limit (and cost a fortune in tokens).

To prevent this, MCP Server developers must implement context-management strategies within the resource definition:

- **Tailing:** Only returning the last _N_ lines (e.g., `tail -n 100`).
    
- **Filtering:** Using URI templates to enforce narrow queries (e.g., `logs://production/auth-service?level=ERROR`).
    
- **Tool-Assisted Pagination:** Often, developers will use a `@mcp.tool()` to search or paginate through logs, and only use `@mcp.resource()` to expose a summarized "current status" document.

> [!summary] Summary 
> The Model Context Protocol (MCP) is primarily a transport and messaging layer. Therefore, **security, authentication, and permissions are not natively baked into the protocol's core; they are implemented at the Transport layer (HTTP/OS) and within your Server's application logic.** Securing an internal database requires a combination of OS-level controls, strict authorization logic within the tool definitions, and standard enterprise auth patterns (like OAuth or API keys) for remote connections.

---

## 1. Authentication: Proving Identity

How authentication is handled depends entirely on the **Transport Layer** you choose for your MCP Server.

> [!info] Local Transport (Stdio)
> When a client (like Claude Desktop) launches an MCP server locally via `stdio`, it relies on **OS-level security**. 
> - The server runs under the same OS user account as the client.
> - **Security Mechanism:** If the user's OS profile has access to the database credentials (e.g., via environment variables, local `.env` files, or keychain), the server has access. 
> - *Best Practice:* Use environment variables injected at startup rather than hardcoding credentials.

> [!info] Remote Transport (SSE / HTTP)
> When hosting an MCP server remotely (e.g., a corporate internal server accessed via Server-Sent Events), you use **standard web authentication**.
> - **Security Mechanism:** The MCP Client must be configured to pass authentication tokens (e.g., Bearer tokens, API keys, or mTLS certificates) in the HTTP headers during the initial connection handshake.
> - The MCP Server validates these headers using standard middleware (e.g., FastAPI's auth dependencies) before upgrading the connection to MCP.

---

## 2. Authorization & Permission Scopes

Once authenticated, what is the AI allowed to do? In MCP, **the Server is the ultimate gatekeeper.** * **Tool-Level Routing:** Scopes are not managed by the AI; they are strictly enforced by the Python/Node backend. If a user authenticates with a "Read-Only" role, your server logic should dynamically return a filtered list of `tools` and `resources` during the `list_tools` request.
* **The "No Raw SQL" Rule:** You should almost never expose a tool that accepts arbitrary SQL queries (e.g., `run_sql(query: str)`). This is a massive vector for prompt injection.
* **Granular Tool Design:** Instead of broad access, expose highly scoped, parameter-validated tools. 
	* *Bad:* `update_database(table, data)`
	* *Good:* `update_employee_status(employee_id: int, status: str)` -> The server then sanitizes these specific inputs and executes a parameterized database query.

---

## 3. Human-in-the-Loop (HITL)

A critical layer of MCP security relies on the **Client Application's UI**. 

> [!warning] Mutating Actions
> AI models can hallucinate or misinterpret user intent. For any tool that modifies sensitive internal databases (POST/PUT/DELETE equivalents), the standard industry pattern is to implement **Human-in-the-Loop (HITL)**.

* **How it works:** When the AI agent decides to call `delete_user_record`, the MCP Client (like Claude Desktop or Cursor) pauses execution and presents a UI prompt to the human user: *"The AI wants to execute `delete_user_record` with arguments `{"id": 405}`. Approve or Reject?"*
* **Responsibility:** This is a Client-side feature, but Server developers should design their tools assuming this workflow will occur for sensitive actions.

---

## 4. Data Exfiltration & Privacy

When connecting an internal database to an external LLM via MCP, the data flows from:
`Database -> MCP Server -> MCP Client -> External LLM Provider (e.g., Anthropic, OpenAI)`.

> [!info] Enterprise Data Agreements
> To prevent sensitive internal database records from being used to train public models, organizations must ensure their MCP Client is connected to an Enterprise or API tier of the LLM provider. Most major providers offer zero-data-retention and zero-training guarantees for their enterprise API endpoints.
