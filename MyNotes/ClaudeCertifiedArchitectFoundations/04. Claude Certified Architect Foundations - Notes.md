### Mechanics Worth Memorizing[cite: 1]
*   `stop_reason`, `tool_use`, `tool_result`, and matching `tool_use_id` in the agent loop.[cite: 1]
*   The exam-guide subagent spawning pattern: `Task` must be available to the coordinator, and context must be passed explicitly.[cite: 1]
*   `tool_choice`: `auto` may answer or call a tool; `any` requires some tool call; a specific tool forces that tool.[cite: 1]
*   **PreToolUse vs PostToolUse:** prevent before execution; validate or normalize after execution.[cite: 1]
*   **Grep vs Glob vs Bash:** file contents, file paths, shell commands.[cite: 1]
*   **CLAUDE.md scopes:** `/memory` for memory/instruction inspection and `/context` for broader current context diagnostics.[cite: 1]
*   **Claude Code CI:** `-p` / `--print` for non-interactive execution and structured JSON for machine parsing.[cite: 1]
*   **Message Batches:** 50% pricing, up to 24 hours, out-of-order results, and `custom_id` correlation.[cite: 1]

## DOMAIN 1 | 27%: Agentic Architecture & Orchestration[cite: 1]

### 1.1 Agentic Loops[cite: 1]
**What it means:** An agent is a controlled loop in which Claude can reason, request a tool, receive the result, reason again, and continue until it reaches a stopping condition.[cite: 1]
**How it works:** Inspect the structured response. When `stop_reason` is `tool_use`, execute the requested tool, append the assistant `tool_use` block to history, then append the `tool_result` block in a user message with the matching `tool_use_id`.[cite: 1]
> [!example] **SIMPLE EXAMPLE:** A purchase-order agent receives a request, calls a tool, gets records, and decides if it can answer or needs another tool.[cite: 1]
> [!warning] **COMMON TRAP:** Stopping because the response contains a text block. Content type is not a safe completion test.[cite: 1]

### 1.2 Multi-Agent Orchestration[cite: 1]
**What it means:** Breaking one larger goal into work owned by specialized agents, with an orchestration pattern deciding delegation and synthesis.[cite: 1]
**How it works:** A common pattern is **hub-and-spoke**: a coordinator delegates focused tasks to specialists, receives their outputs, and synthesizes the final answer.[cite: 1]
> [!warning] **COMMON TRAP:** Treating orchestration as a fixed one-shot fan-out, or over-engineering a simple request.[cite: 1]

### 1.3 Subagent Invocation and Context Passing[cite: 1]
**What it means:** A subagent is a focused worker with its own context and tool permissions.[cite: 1] The specialist does not automatically inherit the parent's conversation history.[cite: 1]
**How it works:** Delegation uses the `Task` mechanism. Pass the goal, relevant facts, constraints, and output format explicitly.[cite: 1]

### 1.4 Workflow Enforcement and Handoff[cite: 1]
**What it means:** Mandatory workflow invariants need a control outside the model, such as a hook, permission rule, state check, or application gate.[cite: 1]
**How it works:** Before a sensitive tool executes, verify the prerequisite state.[cite: 1] For human handoff, pass a structured packet (identifiers, diagnosis, etc.).[cite: 1]
> [!abstract] **EXAM LENS:** Words such as "must", "cannot", and "requires approval" are clues that a deterministic mechanism is needed.[cite: 1]

### 1.5 Agent SDK Hooks[cite: 1]
**What it means:** Hooks let your application intervene at a known moment instead of hoping the model remembers an instruction.[cite: 1]
**How it works:** 
*   **PreToolUse:** Fires before the tool executes (allow, deny, modify).[cite: 1]
*   **PostToolUse:** Fires after execution (validate, normalize, log).[cite: 1]

### 1.6 Task Decomposition Strategies[cite: 1]
**What it means:** Breaking complex work into tasks. Fixed chain vs. adaptive planning.[cite: 1]
**How it works:** Use prompt chaining for predictable multi-aspect work. Use dynamic decomposition for open-ended investigation.[cite: 1]

### 1.7 Session State and Resumption[cite: 1]
**What it means:** Resuming keeps the earlier reasoning context. Forking creates a new branch from a shared baseline.[cite: 1]
> [!warning] **COMMON TRAP:** Treating a resumed session as if it automatically detects every change in the outside world (re-check state!).[cite: 1]

## DOMAIN 2 | 18%: Tool Design & MCP Integration[cite: 1]

### 2.1 Tool Interface Design[cite: 1]
**What it means:** The contract Claude sees: tool name, description, and input schema.[cite: 1]
> [!warning] **COMMON TRAP:** Adding prompt keywords to compensate for ambiguous tool interfaces.[cite: 1]

### 2.2 Structured Error Responses[cite: 1]
**What it means:** The agent needs to distinguish temporary outages from invalid inputs or policy rejections.[cite: 1]
**How it works:** Use `isError` to signal tool-level failure. Return structured details like error category and retry guidance.[cite: 1]

### 2.3 Tool Distribution and Tool Choice[cite: 1]
**How it works:** Scope tools to the agent's role. `tool_choice` modes (`auto`, `any`, specific) control tool invocation, not workflow ordering.[cite: 1]

### 2.4 MCP Server Integration[cite: 1]
**What it means:** Model Context Protocol connects Claude to external systems.[cite: 1]
**How it works:** Configuration can live in `.mcp.json`. Primitives include tools (functions), resources (data/context), and prompts (templates).[cite: 1]

### 2.5 Built-in Tools[cite: 1]
*   **Grep:** Searches inside file contents.[cite: 1]
*   **Glob:** Matches file paths.[cite: 1]
*   **Bash:** Runs shell commands.[cite: 1]
*   **Read / Edit / Write:** File operations.[cite: 1]

## DOMAIN 3 | 20%: Claude Code Configuration & Workflows[cite: 1]

### 3.1 CLAUDE.md Hierarchy, Scoping, and Modular Organization[cite: 1]
**How it works:** 
*   User-level: `~/.claude/CLAUDE.md`[cite: 1]
*   Project-level: `./CLAUDE.md`[cite: 1]
*   Use `/memory` to inspect relevant memory/instruction files.[cite: 1]

### 3.2 Custom Slash Commands and Skills[cite: 1]
**What it means:** On-demand workflows vs. always-on guidance.[cite: 1]
**How it works:** `context: fork` runs the skill in an isolated subagent context.[cite: 1]

### 3.3 Path-Specific Rules for Conditional Convention Loading[cite: 1]
**How it works:** `.claude/rules/` supports `paths:` frontmatter with glob patterns to load conventions only when files are relevant.[cite: 1]

### 3.4 Plan Mode vs Direct Execution[cite: 1]
**What it means:** Plan mode is for exploration/design; direct execution is for clear, mechanical changes.[cite: 1]
> [!abstract] **EXAM LENS:** Read the condition behind the scary number. "60 files" does not automatically mean plan mode.[cite: 1]

### 3.5 Iterative Refinement Techniques[cite: 1]
**How it works:** Provide representative input/output examples or give Claude a verification loop (e.g., failing tests).[cite: 1]

### 3.6 CI/CD Integration[cite: 1]
**How it works:** Use `-p` or `--print` for non-interactive execution. Use `--output-format json` and `--json-schema` for structured parsing.[cite: 1]

## DOMAIN 4 | 20%: Prompt Engineering & Structured Output[cite: 1]

### 4.1 System Prompts with Explicit Criteria[cite: 1]
**What it means:** Define testable criteria instead of vague instructions like "use good judgment."[cite: 1]

### 4.2 Few-Shot Prompting[cite: 1]
**How it works:** Show examples that represent common cases, edge cases, and missing-information cases to teach the boundary.[cite: 1]

### 4.3 Structured Output with Tool Use[cite: 1]
**How it works:** Use JSON input schemas. `strict: true` can guarantee schema-conformant tool inputs, though not semantic business correctness.[cite: 1]

### 4.4 Validation, Retry, and Feedback Loops[cite: 1]
**What it means:** Check if an answer is usable. Retry only when the failure is recoverable (e.g., provide exact validation error back to Claude).[cite: 1]

### 4.5 Batch Processing Strategies[cite: 1]
**How it works:** Message Batches API charges 50% of standard pricing. Takes up to 24 hours. Results can arrive out of order, requiring a stable `custom_id`.[cite: 1]

### 4.6 Multi-Instance and Multi-Pass Review[cite: 1]
**How it works:** Generate -> independent review -> revise. A fresh reviewer instance reduces anchoring to the original reasoning context.[cite: 1]

## DOMAIN 5 | 15%: Context Management & Reliability[cite: 1]

### 5.1 Context Window Management[cite: 1]
**How it works:** Protect exact facts (IDs, dates, amounts) in a compact structured note rather than keeping verbose tool outputs.[cite: 1]

### 5.2 Escalation and Ambiguity Resolution[cite: 1]
**What it means:** Explicitly handle gaps or policy exceptions by routing to humans or asking for evidence, rather than guessing.[cite: 1]

### 5.3 Error Propagation in Multi-Agent Systems[cite: 1]
**How it works:** Propagate structured context upstream (what failed, attempts made, missing coverage) so the coordinator can make decisions.[cite: 1]

### 5.4 Codebase Exploration and Context Degradation[cite: 1]
**How it works:** Use Grep and Glob to narrow files down. Do not bulk-read the entire repository into context.[cite: 1]

### 5.5 Human Review and Confidence Calibration[cite: 1]
**What it means:** Calibrate model confidence scores against real labeled outcomes before trusting them for automated routing.[cite: 1]

### 5.6 Information Provenance and Multi-Source Synthesis[cite: 1]
**How it works:** Preserve structured claim-source mappings through summarization and synthesis to maintain attribution.[cite: 1]

## SECTION 7: Seven Patterns that Resolve Many Difficult Questions[cite: 1]

1.  **Structural control beats prompt-only control when the requirement is a guarantee**[cite: 1]
2.  **Ask what actually changed** (If routing breaks, fix tool contracts or prompts).[cite: 1]
3.  **The "sounds big" trap** (Ambiguity and risk decide plan mode, not file count).[cite: 1]
4.  **Schema guarantees shape, not business truth**[cite: 1]
5.  **A larger context window is not a universal reliability fix**[cite: 1]
6.  **Independent review is about a different evaluation context**[cite: 1]
7.  **Run the mechanism check** (Does the option contain the working mechanism?).[cite: 1]
