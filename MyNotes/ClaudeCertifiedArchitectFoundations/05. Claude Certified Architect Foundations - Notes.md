DOMAIN 1  |  27%

Agentic Architecture & Orchestration

WHAT THIS DOMAIN IS REALLY ASKING

Can the system take a goal, decide what happens next, use tools, delegate work when useful, and still remain controlled and
observable?

1.1  Agentic Loops

Design and implement agentic loops for autonomous task execution.

What it means: An agent is not a single model call. It is a controlled loop in which Claude can reason, request a tool, receive
the result, reason again, and continue until it reaches a stopping condition.

How it works: Your application sends the conversation to Claude and inspects the structured response. When `stop_reason`
is `tool_use`, execute the requested tool or tools, append the assistant `tool_use` block to history, then append the
corresponding `tool_result` block in a user message with the matching `tool_use_id`. Send the updated history back to
Claude. `end_turn` is the normal completion signal. Other stop reasons such as token limits or refusal should be handled
explicitly rather than treated as success.

SIMPLE EXAMPLE

EXAM LENS

A purchase-order agent receives "show me the overdue POs for
supplier A." Claude calls `search_purchase_orders`. The
application executes it, returns the records, and Claude then
decides whether it has enough information to answer or needs
another tool.

Prefer the API or SDK control signal over parsing natural-language
text. An iteration cap is useful as a safety guardrail, but it should
not be the primary definition of task completion.

COMMON TRAP

Stopping because the response contains a text block. Claude can return text and tool calls in the same response, so content
type is not a safe completion test.

Remember it this way: Claude decides the next action. Your application owns the loop and the safety boundaries.

1.2  Multi-Agent Orchestration

Choose and implement orchestration patterns for multiple specialized agents.

What it means: Multi-agent architecture means breaking one larger goal into work owned by specialized agents, with an
orchestration pattern that decides who delegates, who combines results, and how failures are handled.

How it works: A common exam pattern is hub-and-spoke: a coordinator owns the overall request, delegates focused tasks to
specialists, receives their outputs, and synthesizes the final answer. Independent work can fan out in parallel; dependent
work stays sequential. The coordinator should also inspect returned results for coverage. If a specialist exposes a gap, the
coordinator can delegate a targeted follow-up before synthesis. That iterative delegate -> inspect -> delegate again pattern is
more agentic than a one-shot fan-out pipeline. Central coordination improves observability and consistent error handling,
but it adds cost and latency, so specialization should earn its complexity.

SIMPLE EXAMPLE

EXAM LENS

A research coordinator asks a financial-data agent for
quantitative facts, a policy agent for regulations, and a
document-analysis agent for source evidence. The policy result is
missing the effective date, so the coordinator sends one focused

Choose multi-agent design because the work is decomposable,
parallel, context-heavy, or requires different tool permissions. If
the returned work reveals a specific gap, a targeted second
delegation is better than blindly synthesizing incomplete results.

COMMON TRAP

Treating orchestration as a fixed one-shot fan-out, or over-engineering a simple request with several agents when one agent
already has the data and tools needed to finish it.

Remember it this way: Coordinate, inspect coverage, then delegate again only when the result creates a real need.

1.3  Subagent Invocation and Context Passing

Invoke subagents and pass enough context for them to succeed without bloating the parent context.

What it means: A subagent is a focused worker with its own context and tool permissions. In the exam-guide coordinator-
subagent pattern, the coordinator must have the mechanism that can spawn the specialist, and the specialist does not
automatically inherit the parent's conversation history.

How it works: Exam-guide framing: delegation uses the `Task` mechanism, so the coordinator's `allowedTools` must include
`Task`. A specialist definition carries a name or description, its own instructions, and a restricted tool set so the coordinator
can route work appropriately. Pass the goal, relevant facts, constraints, required output format, and success criteria
explicitly in the task prompt. Give the specialist only the tools it needs. Independent tasks can be spawned in parallel when
latency matters. The parent should receive a compact result rather than the specialist's entire intermediate exploration.
Claude's product surfaces evolve, so current interfaces may use newer agent terminology, but for CCAR-F answer according
to the published exam-guide mechanism.

SIMPLE EXAMPLE

EXAM LENS

A contract-review coordinator has `Task` available and delegates
the liability section to a legal-analysis specialist. The task includes
the relevant contract text, the date range, review criteria,
required citations, and a structured risk format. A second
independent section can be delegated in parallel.

If the prompt says 'delegate' but the coordinator keeps doing the
work itself, check whether the spawning mechanism is actually
allowed. If a spawned specialist gives a weak answer, check the
context and output contract before changing the model.

COMMON TRAP

Assuming a subagent automatically knows facts from the parent conversation, forgetting to enable the spawning mechanism,
or sending the entire parent transcript when only a small subset is relevant.

Remember it this way: Spawning is a mechanism. Context passing is a contract. You need both.

1.4  Workflow Enforcement and Handoff

Enforce mandatory workflow rules and create useful handoffs when work moves to another actor.

What it means: Prompts are good for guidance. Mandatory workflow invariants need a control outside the model, such as a
hook, permission rule, state check, or application gate.

How it works: Before a sensitive tool executes, verify the prerequisite state. If the prerequisite is missing, block the tool and
return a structured reason that helps Claude choose the correct next action. For human handoff, pass a structured packet
with the identifiers, diagnosis, relevant amounts or evidence, attempted actions, and recommended next step. Do not make
the human reconstruct the case from a raw transcript.

1.5  Agent SDK Hooks

Use lifecycle hooks to inspect, block, modify, log, or react to agent behavior at defined control points.

What it means: Hooks are programmatic callbacks around agent lifecycle events. They let your application intervene at a
known moment instead of hoping the model remembers an instruction.

How it works: Hooks run at defined lifecycle points. `PreToolUse` fires after Claude proposes a tool call but before the tool
executes, so it can inspect inputs, allow, deny, request approval, or modify the proposed call. `PostToolUse` fires after a
successful tool call, so it can validate, normalize, redact, log, or add context to the result Claude will reason over. A post-tool
hook cannot undo an irreversible side effect that already happened. Other hook events exist, but the exam distinction to
internalize is timing: prevent before execution; validate or normalize after execution.

SIMPLE EXAMPLE

EXAM LENS

Before `process_refund` runs, a `PreToolUse` hook checks
`identity_verified` and the amount and can block the call.
Separately, a supplier-status tool returns dates and status codes
in inconsistent formats; a `PostToolUse` hook normalizes them
into one contract before Claude reasons over the result.

Match the hook to the moment of control. Preventing an action
belongs before execution. Normalizing or validating a successful
result belongs after execution.

COMMON TRAP

Using `PostToolUse` for a rule that must prevent an irreversible action, or using `PreToolUse` when the real problem is
inconsistent output returned by a tool.

Remember it this way: Pre controls the action. Post controls what Claude receives after the action.

1.6  Task Decomposition Strategies

Break complex work into the right sequence of smaller tasks without losing global coherence.

What it means: Decomposition is about deciding whether the work is predictable enough for a fixed chain or open-ended
enough to need adaptive planning.

How it works: For predictable multi-aspect work, prompt chaining can use a fixed sequence: analyze parts, then integrate.
For open-ended investigation, use dynamic decomposition: map the problem, prioritize high-value areas, inspect findings,
and revise the plan as new dependencies appear. These patterns can be combined. Splitting by file or section can also reduce
attention dilution before a final synthesis pass.

EXAM LENS

For a 20-file architecture review, first review each service against
the same rubric, then run a cross-service synthesis to find

Remember it this way: The key axis is predictability and dependency, not task size.

1.7  Session State and Resumption

Continue, branch, or restart sessions while managing stale context and external state.

What it means: A session preserves conversation state. Resuming keeps the earlier reasoning context. Forking creates a new
branch from a shared baseline so two approaches can diverge independently.

How it works: Use resume when the prior context is still useful. Use a fork when you want an independent branch without
redoing the shared analysis. Remember that session history is not the same thing as the current filesystem, database, or
business system. Old tool results can become stale, so re-read or re-query facts that may have changed. If the session is
heavily contaminated with obsolete state, a new session plus a concise structured summary can be cleaner.

SIMPLE EXAMPLE

EXAM LENS

Yesterday a coding agent analyzed a module. Today you want to
compare two refactoring designs from that exact analysis. Fork
the session into two branches. If the source files changed
overnight, re-read the changed files in each branch before
trusting the old findings.

Separate "conversation continuity" from "external-state
freshness." Resuming does not guarantee that earlier tool
outputs are still current.

COMMON TRAP

Treating a resumed session as if it automatically detects every change in the outside world.

Remember it this way: Resume context. Re-check state.

Tool Design & MCP Integration

WHAT THIS DOMAIN IS REALLY ASKING

Can Claude reliably discover the right capability, send valid inputs, interpret results and errors, and stay inside the right
integration and permission boundary?

2.1  Tool Interface Design

Design tool interfaces that the model can select and call reliably.

What it means: A tool interface is the contract Claude sees: tool name, description, and input schema. Good backend code
cannot compensate for an ambiguous contract.

How it works: Use a specific name, explain the purpose, describe the expected inputs and outputs, and state when to use
this tool versus a similar one. In JSON Schema, `properties` are the fields Claude can send, and `required` lists the fields that
must be present. Prefer purpose-specific interfaces over one giant generic tool with many loosely related modes.

SIMPLE EXAMPLE

EXAM LENS

`check_po_status` takes required `po_id: string` and optional
`include_history: boolean`. Its description says it retrieves the
current lifecycle status of one purchase order. A separate
`search_purchase_orders` tool is for finding POs by supplier,
date, or status.

When two tools are confused, look for overlapping names, vague
descriptions, or missing intent boundaries before changing
models or adding routing infrastructure.

COMMON TRAP

Adding more prompt keywords to compensate for two tools whose interfaces are genuinely ambiguous. The ambiguity is still
present and may fail in the opposite direction.

Remember it this way: The description is part of the routing logic.

2.2  Structured Error Responses

Return errors that tell the agent what failed and what recovery is possible.

What it means: "Operation failed" is not enough. The agent needs to distinguish a temporary outage from invalid input, a
policy rejection, or missing permission.

How it works: MCP tool results can use `isError` to signal tool-level failure. Beyond that protocol flag, your application can
return structured details such as error category, human-readable message, retry guidance, and partial results. A valid empty
result should usually remain a successful result, not be mislabeled as an error. Retry only when the failure is actually
retryable.

SIMPLE EXAMPLE

EXAM LENS

A supplier API returns HTTP 503. The tool returns `isError: true`,
category `transient`, and guidance that one bounded retry is
allowed. A refund blocked by policy returns category
`business_policy` and `retryable: false`.

Look for the recovery path. The best error design helps the agent
decide whether to retry, correct inputs, ask for access, choose
another path, or escalate.

COMMON TRAP

Retrying every failure the same number of times. Repeated retries on policy or permission errors add latency and can create
unsafe behavior.

Remember it this way: An error should help the next decision.

2.3  Tool Distribution and Tool Choice

Give each agent the right tool set and use tool-choice controls for the right purpose.

What it means: Tool distribution is a context and routing decision. An agent that sees many irrelevant or overlapping tools
has a harder selection problem and a larger attack or error surface.

How it works: Scope tools to the agent's role and keep cross-role access intentional. Claude APIs support tool-choice modes
such as `auto` (Claude may answer or call a tool), `any` (Claude must call a tool and chooses which one), and a specific
named tool. These settings control tool invocation, not the ordering of an entire workflow. Modern Claude Code can also
defer some MCP tool schemas until needed, reducing context pressure, but clear scoping still matters.

SIMPLE EXAMPLE

EXAM LENS

A billing agent gets account lookup, invoice lookup, and payment
tools. It does not need code-editing or supplier-contract tools.
For a structured extraction request where a tool call is
mandatory, force tool use. For a normal support conversation,
`auto` may be appropriate.

Ask what the control actually guarantees. `tool_choice=any`
guarantees some tool call, not "verify identity before refund."

COMMON TRAP

Using tool choice as a substitute for workflow state or prerequisite checks.

Remember it this way: Tool selection and workflow enforcement are different problems.

2.4  MCP Server Integration

Connect Claude to external systems through MCP with the right scope, transport, credentials, and primitive.

What it means: MCP is a standard client-server protocol for exposing capabilities and context to AI applications. It reduces
custom integration plumbing, but it does not remove the need for good tool design, authentication, or least privilege.

How it works: In Claude Code, project-scoped MCP configuration can live in `.mcp.json` and be shared through version
control. Local and user scopes are private and stored in user configuration. Environment-variable expansion lets teams
reference secrets without committing them. For remote servers, current Claude Code documentation favors HTTP; legacy
SSE configurations may still exist. MCP defines three major server primitives: tools for model-invoked functions, resources
for application-controlled context/data, and prompts for reusable user-controlled prompt templates.

SIMPLE EXAMPLE

EXAM LENS

A team adds a project-scoped Jira MCP server in `.mcp.json`,
references `${JIRA_TOKEN}` rather than committing the token,
and exposes a narrow `get_issue` tool plus resources for read-
only project metadata.

Choose scope based on who needs the server. Choose a tool
when the model needs to invoke a function. Choose a resource
when exposing readable context is the better fit. Prefer an
existing trusted server when it meets the requirement; build
custom behavior when the organization needs a specific contract
or policy.

Putting personal credentials directly into the repository, or creating a custom server for a standard integration without a real

2.5  Built-in Tools

Choose Claude Code built-in tools based on whether you are looking for content, paths, or a file operation.

What it means: The exam expects you to know the practical difference between common built-in tools. The choice should
match the information you need, not the size of the repository.

How it works: `Grep` searches inside file contents for symbols, imports, error strings, or other text. `Glob` matches file paths
and filename patterns. `Read` loads a file. `Edit` makes a targeted change. `Write` creates or replaces file content. `Bash`
runs shell commands such as tests, builds, package commands, or Git operations. For unfamiliar repositories, search first,
read selectively, and follow references instead of loading everything. If an `Edit` target is ambiguous, re-read the file and use
a more unique anchor. If a precise edit is no longer practical and a whole-file rewrite is genuinely safer, use Read + Write
rather than guessing at an ambiguous edit.

SIMPLE EXAMPLE

EXAM LENS

To find every caller of `calculateTax`, use `Grep`. To find every
`*.test.tsx` path, use `Glob`. To run `npm test`, use `Bash`. After
locating the correct file, use `Read` and `Edit`; if the edit anchor
appears in six places, narrow the anchor before changing
anything.

Translate the question into one of three categories: inside file
contents, file paths, or an actual shell command. That usually
points to Grep, Glob, or Bash. Then use Read/Edit/Write only on
the files you have narrowed down.

COMMON TRAP

Bulk-reading hundreds of files for 'complete context', or reaching for Bash when a purpose-built search or file tool is safer and
clearer.

Remember it this way: Search contents with Grep, paths with Glob, commands with Bash, then edit narrowly.

Claude Code Configuration & Workflows

WHAT THIS DOMAIN IS REALLY ASKING

Can a team make Claude Code behave consistently across people, repositories, file types, workflows, and automated pipelines?

3.1  CLAUDE.md Hierarchy, Scoping, and Modular Organization

Place persistent instructions at the right level so the right people and files receive them.

What it means: `CLAUDE.md` is persistent guidance for Claude Code. Its location controls scope. This is less about
memorizing paths and more about asking "who should see this instruction?"

How it works: Typical scopes include user-level `~/.claude/CLAUDE.md` for personal guidance, project-level `./CLAUDE.md`
or `./.claude/CLAUDE.md` for team-shared instructions, and `CLAUDE.local.md` for private project-specific notes. Nested
CLAUDE.md files can load when Claude works in those areas. `@import` can keep instruction sets modular, while
`.claude/rules/` supports topic-specific and path-specific organization. For the exam, know `/memory` as the direct
command for listing and inspecting CLAUDE.md, local memory, and rules files. In current Claude Code, `/context` is a broader
diagnostic that shows the live context breakdown and which memory files are loaded.

SIMPLE EXAMPLE

EXAM LENS

Your team has a testing standard that every developer should
get. If it only lives in your home-directory CLAUDE.md,
teammates will not inherit it. Move the shared standard to
project scope and commit it. Use `/memory` to inspect the
relevant memory/instruction files; use `/context` when you want
the broader live context picture.

When the symptom is 'works for me but not for my teammate,'
inspect configuration scope first. For CCAR-F questions centered
on memory or CLAUDE.md loading, remember the exam-guide
`/memory` framing; `/context` is the broader current-product
diagnostic.

COMMON TRAP

Copying personal configuration by email to every teammate, or memorizing a command name without understanding that the
real issue is configuration scope.

Remember it this way: First ask who should receive the instruction. Then put the file at that scope.

3.2  Custom Slash Commands and Skills

Package reusable, task-specific workflows so they load when needed rather than bloating always-on context.

What it means: Commands and skills are reusable instructions for a particular job. A good distinction is always-on project
guidance versus an on-demand workflow.

How it works: Project commands and skills can be committed under `.claude/`, while personal ones live in the user
configuration area. A `SKILL.md` can include frontmatter that controls behavior. `context: fork` runs the skill in an isolated
subagent context and returns its result, useful for verbose exploration. `allowed-tools` can restrict tools for Claude Code skill
execution. `argument-hint` is an autocomplete hint that shows expected arguments; it is not a validation engine that
magically asks for missing fields.

3.3  Path-Specific Rules for Conditional Convention Loading

Load conventions only when the files they apply to are relevant.

What it means: Path-specific rules prevent every coding convention from appearing in every context. They are especially
useful when one file type is scattered across many directories.

How it works: A file in `.claude/rules/` can use `paths:` frontmatter with glob patterns. The rule is activated when Claude
reads or works with matching files, keeping unrelated conventions out of context. A directory-level CLAUDE.md can also be
appropriate when the convention naturally maps to one subtree. Choose by the shape of the repository.

SIMPLE EXAMPLE

EXAM LENS

All `*.test.tsx` files across 15 directories must follow the same
mocking convention. One rule with `paths: ["**/*.test.tsx"]` is
cleaner than adding a CLAUDE.md to every directory.

If the rule is based on file type across the repository, a glob is
often the natural fit. If the rule belongs to one subsystem,
directory scope may be simpler.

COMMON TRAP

Making a universal root rule for a narrow convention and paying the context cost on every unrelated task.

Remember it this way: Scope instructions to where they are useful.

3.4  Plan Mode vs Direct Execution

Decide when Claude should analyze and design before changing files.

What it means: Plan mode is for exploration and design when the right implementation is not yet obvious or the cost of a
wrong change is high. Direct execution is appropriate when the transformation is clear and mechanical.

How it works: In plan mode, Claude can inspect and reason without making source edits, then present a plan for approval.
The decision is driven by ambiguity, architectural choice, risk, and rework cost, not simply the number of files. A large but
deterministic rename can be executed directly; a two-file authentication redesign may deserve planning.

SIMPLE EXAMPLE

EXAM LENS

Renaming one deprecated function in 60 files with one obvious
replacement is mechanical. Reworking an authentication
boundary with three valid approaches should be planned first,
even if only a few files are involved.

Read the condition behind the scary number. "60 files" does not
automatically mean plan mode.

COMMON TRAP

Using file count as the only trigger for plan mode.

3.5  Iterative Refinement Techniques

Give Claude objective feedback so each iteration is driven by evidence rather than vague preference.

What it means: Refinement works best when the system can compare an output with something concrete: tests, examples,
schemas, expected behavior, or explicit acceptance criteria.

How it works: Provide representative input/output examples when prose instructions are being interpreted inconsistently.
For code, give Claude a verification loop: reproduce the bug, write or run tests, make a focused change, and re-run the
checks. In unfamiliar domains, an interview pattern can surface missing design decisions before implementation. Keep
independent changes separable so one failure does not obscure another.

SIMPLE EXAMPLE

EXAM LENS

A code-review agent keeps missing a specific API-contract
violation. Add a failing test or a concrete positive/negative

WHAT THIS DOMAIN IS REALLY ASKING

5.1  Context Window Management

Keep the most decision-relevant information available as conversations and tool outputs grow.

What it means: Context is the working set Claude can attend to in the current request. More context is not automatically
better context. Long sessions can accumulate repeated instructions, verbose tool outputs, and old facts that compete with
what matters now.

How it works: Protect exact facts such as IDs, dates, amounts, and user requirements in a compact structured note rather
than allowing them to be repeatedly paraphrased. Trim large tool outputs to relevant fields. Use clear sectioning and place
critical constraints where they are easy to find. Claude Code can compact long sessions, and `/compact` can be used
explicitly. Subagents can isolate verbose exploration. A larger context window can be useful, but it does not fix poor
information architecture by itself.

EXAM LENS

missing information or attention dilution. The fixes are different.

Automatically switching to a bigger context window without trimming irrelevant output or protecting exact facts.

How it works: If the customer explicitly requests a human and the scenario policy says to honor that request, escalate
immediately. If multiple records could match, ask for another identifier rather than choosing heuristically. If the policy has a
real gap or an exception outside the agent's authority, route it to the appropriate human or policy owner. Frustration alone
is not always the same as an explicit escalation request.

SECTION 7

Seven patterns that resolve many difficult
questions

These are exam heuristics, not universal laws. Use them only when the scenario conditions support
them.

1. Structural control beats prompt-only control when the requirement is a
guarantee

If an action must never occur without a prerequisite, a prompt can help behavior but a gate, permission, hook, or workflow
state is what enforces the invariant.

2. Ask what actually changed

If routing breaks immediately after a prompt change while tool interfaces did not change, inspect the new prompt before
redesigning the tool layer. If two tool descriptions were always vague, fix the tool contracts.

3. The "sounds big" trap

A 60-file mechanical rename can be simpler than a two-file architectural redesign. Use ambiguity and rework cost to decide
planning, not the size words in the stem.

4. Schema guarantees shape, not business truth

Valid JSON can contain an invalid invoice total. Use schemas for structure and a separate validation layer for semantics.

5. A larger context window is not a universal reliability fix

Use more context when missing information is the real problem. Use trimming, structure, compaction, subagents, or
persistent exact facts when attention dilution is the problem.

6. Independent review is about a different evaluation context

A fresh review pass can reduce anchoring, especially when it receives the artifact plus a rubric rather than the generator's
reasoning. It is not magic, and it does not replace tests or validation.

7. Run the mechanism check

Before choosing an answer, ask: does this option contain the mechanism that produces the stated result, or does it only
restate the problem in better words?
