# Runtime - Session State and Memory Management

### ADK Runtime 

**Reference:** https://google.github.io/adk-docs/runtime/

> [!summary] Google ADK Runtime Overview
> The [[Google ADK]] Runtime acts as the central engine or "nervous system" for your agentic applications. It handles the iterative loop of receiving user inputs, invoking models, executing tools, and maintaining context. 

#### Core Runtime Components

* **[[Runner]] (Primary Class):** The main orchestrator. It manages the event loop, connects agents to sessions, passes context, executes tool calls, and updates the session with new events and state changes. Think of it as the "main librarian" coordinating tasks.
* **[[Service]] (External Services):** Interfaces for persisting data or connecting to external systems, such as the `SessionService` for conversation tracking and `MemoryService` for long-term knowledge retrieval.
* **[[Agent]]:** The reasoning engine (powered by LLMs like Gemini) that processes the input from the Runner, decides whether to use a tool, and yields events back to the Runner.
* **[[Event]]:** A discrete action or message (e.g., user prompt, tool execution result, agent response) that the Runner processes and appends to the session history.

**Component Interaction:**
1. The **Runner** receives a user request and loads the **Session** via a SessionService.
2. It passes the conversation history and **State** to the **Agent**.
3. The **Agent** yields an **Event** (like a tool call or a partial response).
4. The **Runner** processes the event, interacts with external **Services** if needed, updates the **Session** history, and prompts the **Agent** to continue until a final response is reached.

---

### Core Concepts: Session, State, and Memory

> [!info] Understanding Context Management
> To build agents capable of multi-turn, coherent conversations, ADK separates context into three distinct layers:

1. **[[Session]]:** The overarching object that tracks an individual conversation thread. It contains a unique ID, metadata, a chronological log of all interactions (`events`), and a temporary scratchpad (`state`).
2. **[[State]]:** A key-value dictionary that acts as the agent's short-term "scratchpad" during a specific session. It is used to temporarily store dynamic details (like a user's name, current quiz score, or extracted preferences) so the agent doesn't have to ask for them repeatedly.
3. **[[Memory]]:** The agent's Long-Term Knowledge store. Unlike Session and State, Memory persists across multiple different conversations and sessions. It acts like a searchable archive (often backed by a vector database or Vertex AI Memory Bank) that the agent can query to recall past facts.
---
### Session Services Overview

ADK offers three primary implementations for managing session data, depending on your application's lifecycle and scaling needs.

> [!note] Session Service Types
> * **[[In-Memory Session Service]] (`InMemorySessionService`):** Stores all session data (events and state) directly in the application's RAM. 
> * **[[Vertex AI Session Service]] (`VertexAiSessionService`):** Uses Google Cloud's Vertex AI Agent Engine infrastructure. Provides scalable, persistent, and production-ready session management.
> * **[[Database Session Service]] (`DatabaseSessionService`):** Connects to relational databases (like PostgreSQL, MySQL, or SQLite) to persist session data locally or on managed database servers.

#### Code Implementation of Session Services

> [!code] Service Initialization Examples
> Below is how you would initialize each type of session service within the ADK framework.

```python
# 1. In-Memory Session Service (Prototyping)
from google.adk.sessions import InMemorySessionService
memory_service = InMemorySessionService()

# 2. Vertex AI Session Service (Production / Cloud)
from google.adk.sessions import VertexAiSessionService
vertex_service = VertexAiSessionService(
    project_id="my-gcp-project",
    location="us-central1"
)

# 3. Database Session Service (Self-Managed Persistence)
from google.adk.sessions import DatabaseSessionService
db_service = DatabaseSessionService(
    connection_string="sqlite:///adk_sessions.db"
	)
```

### The Challenge with In-Memory Sessions

> [!warning] Volatility of In-Memory Storage 
> 
> The primary challenge with the **[[In-Memory Session Service]]** is that **memory is not retained between application restarts or across distributed servers**.
> 
> Because data is stored purely in the application's RAM, if the server crashes, restarts, or if your application scales horizontally (where Request A goes to Server 1 and Request B goes to Server 2), the session context is entirely lost. To overcome this limitation for production or long-term session management, you must use a persistent layer like the **[[Database Session Service]]** or Vertex AI.

---
### Deep Dive: Database Session Management

> [!info] How Database Session Management Works 
> The **[[Database Session Service]]** resolves the volatility issue by mapping ADK Session objects directly to tables in a relational database.
> 
> **The Flow:**
> 
> 1. **Initialization:** When configured via a connection string, ADK automatically ensures the necessary schema (tables for sessions, states, and event logs) exists in the target database.
>   
> 2. **Retrieval:** When a user sends a message, the [[Runner]] queries the database using the `session_id`. It reconstructs the Session object in memory, fully populated with the historical events and the current state dictionary.
>    
> 3. **Execution & Commitment:** The agent processes the turn. Once the turn is complete, the Runner takes any new events and state updates and commits them back to the database via SQL `INSERT` and `UPDATE` transactions, ensuring data durability.


#### SQLite Implementation Example

> [!code] SQLite DB Session Example 
> Below is a conceptual example of setting up a persistent session using SQLite. This ensures that even if the script is stopped and run again later, the agent will perfectly remember the state of the conversation.

```Python
from google.adk.runners import Runner
from google.adk.agents import LlmAgent
from google.adk.sessions import DatabaseSessionService
import asyncio

async def main():
    # 1. Initialize the Database Session Service with an SQLite file
    # This will create 'agent_sessions.db' in the local directory
    session_service = DatabaseSessionService(
        connection_string="sqlite:///agent_sessions.db"
    )
    
    # 2. Define a basic stateful agent
    agent = LlmAgent(
        name="assistant",
        model="gemini-2.5-flash",
        instruction="You are a helpful assistant. Use context to answer questions."
    )
    
    # 3. Create or load the session persistently
    session = await session_service.create_session(
        app_name="my_local_app",
        user_id="user_123",
        session_id="persistent_session_01"
    )
    
    # 4. Initialize the Runner with the DB service
    runner = Runner(
        agent=agent,
        session_service=session_service
    )
    
    # 5. Run the interaction. The state and events are automatically saved to SQLite.
    events = await runner.run_async(
        user_id="user_123",
        session_id=session.id,
        new_message="Hi, my favorite color is blue."
    )
    
    for event in events:
        if event.is_final_response():
            print(event.content.parts[0].text)

if __name__ == "__main__":
    asyncio.run(main())
```


> [!summary] Does SQLite require a separate installation?
> **No.** You do not need to install a separate database server to use [[SQLite]] with the [[Database Session Service]]. This is one of its biggest advantages for local development and session persistence.
> 
> **Why SQLite is Easy to Use**
> > [!info] Core Advantages
> * **Built into Python:** SQLite comes pre-packaged with Python's standard library. You do not have to download, configure, or run any background database services.
> * **It's Just a Local File:** When you execute your agent code using a connection string like `connection_string="sqlite:///agent_sessions.db"`, the database engine simply creates a standard local file named `agent_sessions.db` directly in your project folder. All of your [[Session Data]], session states, and event logs are safely stored inside that single file.

**Dependencies Note**

> [!warning] Python SQL Libraries
> While you don't need to install the SQLite database engine itself, you *might* need to ensure you have standard Python SQL wrapper libraries installed (such as **[[SQLAlchemy]]**), depending on how [[Google ADK]] maps objects to the database under the hood. 
> 
> *Note: These dependencies are typically included and installed automatically when you install the main ADK package via `pip`.*

### Runtime - Memory Service and Long Term Knowledge
Refer : https://google.github.io/adk-docs/sessions/memory/#the-memoryservice-role

> [!info] Understanding Long-Term Knowledge and Memory Service
> While a [[Session]] tracks the chronological history and temporary [[State]] of a single, ongoing conversation (short-term memory), agents frequently need to recall information from completely different past interactions. 
> 
> The **[[Memory Service]]** manages this **Long-Term Knowledge**. It acts as a searchable archive or knowledge library that the agent can consult, persisting crucial user context, facts, and preferences across multiple sessions.

### Managing Long-Term Knowledge

The underlying `BaseMemoryService` defines the interface for managing this searchable knowledge store. Its primary workflows involve:

1. **Ingesting Information (`add_session_to_memory`):** Taking the contents of a completed [[Session]] and extracting the relevant information to store in the long-term knowledge archive.
2. **Searching Information (`search_memory`):** Allowing an agent (typically via a dedicated `Tool`) to query the knowledge store and retrieve relevant snippets based on a specific user request.

---
### Types of Memory Services

Google ADK offers two distinct implementations of the `MemoryService`, allowing you to scale from local prototyping to cloud-based production.

* **[[InMemoryMemoryService]]:** Stores session information directly in the application's RAM and performs basic keyword matching. It requires no setup and is the default.
* **[[VertexAiMemoryBankService]]:** Uses Google Cloud's Vertex AI to provide advanced semantic search and LLM-powered memory extraction. Instead of just storing raw logs, it uses AI to actually summarize, extract, and consolidate meaningful information into an evolving profile.

> [!summary] Memory Service Comparison

| Feature               | `InMemoryMemoryService`                                     | `VertexAiMemoryBankService`                                                                  |
| :-------------------- | :---------------------------------------------------------- | :------------------------------------------------------------------------------------------- |
| **Persistence**       | None (Data is lost on restart)                              | Yes (Managed securely by Vertex AI)                                                          |
| **Primary Use Case**  | Prototyping, local development, and simple testing.         | Building meaningful, evolving memories from user conversations.                              |
| **Memory Extraction** | Stores the full conversation history as-is.                 | Extracts meaningful information and consolidates it with existing memories (powered by LLM). |
| **Search Capability** | Basic keyword matching.                                     | Advanced semantic search.                                                                    |
| **Setup Complexity**  | None. It is the default.                                    | Low. Requires an Agent Engine instance in Vertex AI.                                         |
| **Dependencies**      | None.                                                       | Google Cloud Project, Vertex AI API.                                                         |
| **When to use it**    | Searching across multiple sessions' chat histories locally. | When you want your agent to persistently remember and learn from past interactions.          |

### Code Implementation: Adding and Retrieving Memory


> [!code] Example: Managing Memory in Python
> The snippet below demonstrates how to capture a completed session, add it to the `MemoryService`, and configure an agent to actively retrieve that long-term knowledge using a memory tool.

```python
import asyncio
from google.adk.agents import LlmAgent
from google.adk.sessions import InMemorySessionService
from google.adk.memory import InMemoryMemoryService
from google.adk.runners import Runner
from google.adk.tools import load_memory

# 1. Initialize the Services
session_service = InMemorySessionService()
memory_service = InMemoryMemoryService()

# 2. Add Memory: Capture a completed session and save to Long-Term Knowledge
async def save_conversation_to_memory(runner, app_name, user_id, session_id):
    # Fetch the completed session
    completed_session = await runner.session_service.get_session(
        app_name=app_name, 
        user_id=user_id, 
        session_id=session_id
    )
    # Extract and add to the Memory Service
    await memory_service.add_session_to_memory(completed_session)
    print("Session successfully added to long-term memory.")

# 3. Retrieve Memory: Define an agent capable of searching its memory
memory_recall_agent = LlmAgent(
    model="gemini-2.5-flash",
    name="MemoryRecallAgent",
    instruction="""
    Answer the user's question. You must use the 'load_memory' tool if the 
    answer might be stored in past conversations or long-term knowledge.
    """,
    tools=[load_memory] # Granting the agent permission to query the memory service
)

# 4. Agent Execution: The runner connects the agent to the memory service
async def ask_agent_with_memory(user_query):
    runner = Runner(
        agent=memory_recall_agent,
        app_name="memory_app",
        session_service=session_service,
        memory_service=memory_service # Attach memory service to the runner
    )
    
    # Run the agent. If it needs context, it will call load_memory() automatically.
    async for event in runner.run_async(
        user_id="user_123", 
        session_id="new_session_02", 
        new_message=user_query
    ):
        if event.is_final_response():
            print(event.content.parts[0].text)
```

### Google ADK - Vertex AI Memory Bank Service

> [!info] What is the Vertex AI Memory Bank Service?
> The **[[VertexAiMemoryBankService]]** is a robust, cloud-based implementation of the ADK memory interface. It leverages Google Cloud's Vertex AI Agent Engine to provide persistent, scalable, and intelligent long-term knowledge storage for your agents. 
> 
> Instead of merely logging raw chat history, it actively processes past conversations using an LLM to extract, consolidate, and store meaningful facts and user preferences.

---

#### Advantages over InMemoryMemoryService

While `InMemoryMemoryService` is great for quick local prototyping, it falls short in production environments. `VertexAiMemoryBankService` provides several critical advantages:

* **True Persistence:** In-memory data is instantly destroyed when the application restarts or crashes. Vertex AI safely stores this data in the cloud, allowing agents to remember users across multiple days, sessions, or device reboots.
* **Intelligent Extraction:** Instead of blindly storing a massive, token-heavy transcript of every conversation, the Memory Bank uses an LLM to summarize and extract only the "meaningful information" (e.g., "User is allergic to peanuts," "User prefers Python over Java").
* **Semantic Search:** In-memory relies on basic keyword matching. Vertex AI uses advanced semantic vector search, meaning it understands the *intent* of the query, finding relevant memories even if the exact words don't match.

---
## Leveraging VertexAiMemoryBankService 

There are two primary architectural patterns for leveraging the Vertex AI Memory Bank:

**1. Direct Deployment (Native Pattern)**
In this standard approach, where one deploy a fully-featured, complex agent directly to the Vertex AI Agent Engine. The agent runs in the cloud, and it natively utilizes its own designated `agent_engine_id` to read and write to its dedicated memory store.

**2. The "Dummy Agent" Pattern (Headless Memory Store)**
Sometimes, there is a need  to run your agent logic elsewhere (e.g., locally, on Cloud Run, or within a separate custom backend) but still want the powerful, managed memory capabilities of Vertex AI. 
* **How it works:** deploy a basic, empty "**Dummy Agent**" to Vertex AI solely to provision an Agent Engine environment and generate an `agent_engine_id`.
* **The Execution:** *real* agent runs locally or on your own servers. It connects to the Vertex AI Session and Memory services using the dummy's `agent_engine_id`. The dummy agent never actually processes prompts; it simply acts as an anchor for the cloud database.

## Code Explanation: Local Agent with Vertex Memory

> [!summary] Code Breakdown
> The code snippet below demonstrates the **Dummy Agent Pattern**. It runs an agent locally while explicitly pointing its session and memory storage to a remote Vertex AI Agent Engine.

**Key Components Explained:**

1.  **Service Initialization:**
    `VertexAiSessionService` and `VertexAiMemoryBankService` are initialized using the `PROJECT_ID`, `LOCATION`, and `agent_engine_id`. This hardwires the local script to the cloud database.
2.  **`add_session_to_memory` (The Callback):**
    This is an asynchronous function designed to run automatically *after* the agent finishes its turn. It accesses the `callback_context` to safely extract the current session and inject it directly into the `memory_service.add_session_to_memory()` method. This ensures the agent "learns" from the conversation without requiring manual save triggers.
3.  **Agent Definition & `PreloadMemoryTool`:**
    The `root_agent` is defined locally. It is equipped with the `PreloadMemoryTool()`, which explicitly grants the agent the ability to query the Vertex AI Memory Bank before or during its response generation to fetch historical context. The `after_agent_callback` is attached here to enable the auto-saving mechanism described above.
4.  **The Runner & Execution (`call_agent`):**
    The `Runner` acts as the orchestrator, binding the local agent to the cloud-based session and memory services. When `call_agent` is executed, it creates a remote session, sends the query ("tell me about world war 2"), and streams the events until the final LLM response is printed.

> [!code] Implementation Example

```python
from typing import Optional
import asyncio
from google.adk.agents import Agent
from google.adk.agents.callback_context import CallbackContext
from google.adk.tools.preload_memory_tool import PreloadMemoryTool
from agent import root_agent
from google.adk.runners import Runner
from google.genai import types
from google.adk.memory import VertexAiMemoryBankService
from google.adk.sessions import VertexAiSessionService
import os

USER_ID = "user"
os.environ["GOOGLE_API_KEY"] = "YOUR-KEY-HERE"
PROJECT_ID='learn-adk-476816'
LOCATION='us-central1'
agent_engine_id='1676548524172378112' # ID of the "Dummy" agent deployed on Vertex

# 1. Connect local execution to Cloud Services
session_service = VertexAiSessionService(
    project=PROJECT_ID, location=LOCATION, agent_engine_id=agent_engine_id
)
memory_service = VertexAiMemoryBankService(
    project=PROJECT_ID, location=LOCATION, agent_engine_id=agent_engine_id
)

# 2. Define the auto-save callback
async def add_session_to_memory(
        callback_context: CallbackContext
) -> Optional[types.Content]:
    """Automatically save completed sessions to memory bank """
    if hasattr(callback_context, "_invocation_context"):
        invocation_context = callback_context._invocation_context
        if invocation_context.memory_service:
            await invocation_context.memory_service.add_session_to_memory(
                invocation_context.session
            )

# 3. Define the Agent with Tools and Callbacks
root_agent = Agent(
    name="history_help_agent",
    model="gemini-2.5-flash",
    description=(
        "Agent to help with historical questions."
    ),
    instruction=(
        "You are a helpful AI agent who can answer to user's historical questions."
    ),
    tools=[
        PreloadMemoryTool() # Allows agent to query past memories
    ],
    after_agent_callback=add_session_to_memory # Triggers the auto-save
)

# 4. Orchestrate the Runner
runner = Runner(
    app_name=root_agent.name,  # type: ignore
    agent=root_agent,
    session_service=session_service,
    memory_service=memory_service,
)

# 5. Execute the interaction
async def call_agent(query, runner):
    session = await session_service.create_session(
        app_name=root_agent.name,  # type: ignore
        user_id=USER_ID,
    )
    content = types.Content(role="user", parts=[types.Part(text=query)])
    events = runner.run(
        user_id=session.user_id, session_id=session.id, new_message=content
    )

    for event in events:
        if event.is_final_response():
            final_response = event.content.parts[0].text
            print("\nAgent Response: ", final_response)


if __name__ == "__main__":
    asyncio.run(call_agent("tell me about world war 2", runner))
