# 🚀 Project Log: Architectural Optimization of Resume Optimizer 

## 💡 The Spark (Ideation & Conception)
The initial `resume_optimizerv2` pipeline was fully functional but suffered from severe architectural bloat. It relied heavily on `LlmAgent` nodes that passed the **entire conversation history** down the chain. 

As the pipeline processed a resume, the context window snowballed. By the 7th agent (the `Critic`), the AI was processing up to 30,000+ tokens just to make a simple decision. This led to:
1. **High Latency:** Slow execution times.
2. **High API Costs:** Wasted tokens on redundant data (like echoing the `raw_text` of a resume multiple times).
3. **Rate Limiting:** Hitting the strict 5 Requests Per Minute (RPM) limits on the Gemini 2.5 Flash free tier.

**The Goal:** Restructure the pipeline to cut token consumption by 60-70% without losing extraction quality, transitioning from brute-force AI to deterministic engineering.

---

## 🧠 Brainstorming with Antigravity Skills
To tackle this, we utilized a suite of specialized AI skills to audit and refactor the codebase:

* **`@context-compression` & `@llm-prompt-optimizer`:** Used to audit the massive 142-line instruction prompts. We removed 40-line JSON examples and verbose synonym tables, making the directives terse and strict.
* **`@prompt-caching`:** Used to identify loops where static instructions were being repeatedly sent to the LLM (specifically in the `ResumeRewriter`), draining the API budget.
* **`@clean-code`:** Used to enforce DRY (Don't Repeat Yourself) principles, such as centralizing the `get_dict_from_state()` utility that was previously copy-pasted across 5 different agent files.
* **`@systematic-debugging`:** Used to trace pipeline crashes back to data-extraction mismatches and fix them without rewriting the entire module.

## 🏗️ What Was Built (The Implementation)

We executed a phased FinOps refactoring plan:

### 1. The "Quick Wins" (Data Hygiene)
* **Stopped the Echo:** Modified the `DocumentParserAgent` schema to stop returning the `raw_text` of the resume, saving ~4,000 tokens per run. Downstream agents were repointed to read from the central `state` dictionary.
* **Prompt Shrinking:** Compressed all system prompts, saving ~3,500 input tokens.

### 2. The Architectural Shift (Zero-LLM Nodes)
> [!success] The highest ROI change in the project.
We realized we were paying an LLM to do basic math. We converted the `AlignmentValidatorAgent` from an expensive `LlmAgent` into a deterministic `PythonTaskNode`. 
* Instead of the AI guessing seniority, we built a Python script to scan job titles against a `SENIORITY_LADDER` dictionary.
* We used strict Python to calculate the numerical seniority gap and domain skill overlap, enforcing a 100% reliable "Hard Gate" for zero tokens.

### 3. Advanced Optimization (Prefix Caching)
In the `ResumeRewriterAgent`, we restructured the prompts. By placing the static Job Description and rewriting rules at the *absolute top* of the prompt (`STATIC_PREFIX`), we triggered Gemini's native Prefix Caching. This massively discounted the token cost for the subsequent job experience loop.

## 🚧 Challenges Faced & Overcome

### Challenge 1: The "Model Not Found" Framework Mismatch
> [!bug] Issue
> While trying to switch to `models/gemma-3-1b-it` to bypass Gemini Flash rate limits, the ADK framework threw a `ValueError: Model not found`, even though the API key had access to it.

**The Fix:** We discovered the ADK `LLMRegistry` uses an internal allowlist and didn't recognize the brand-new Gemma 3 prefix. We bypassed this by utilizing alias endpoints like `models/gemini-flash-latest` which the framework recognized and which routed to a fresh rate-limit bucket.

### Challenge 2: The RPM Rate Limit Wall
> [!bug] Issue
> Because the code was now highly optimized and fast, the `ResumeRewriterAgent` fired 5 asynchronous requests instantly, hitting the 5 RPM limit on Gemini 2.5 Flash and causing `429 Too Many Requests` errors.

**The Fix:** We implemented a strict throttle. We imported `asyncio` and injected an `await asyncio.sleep(15)` delay inside the experience parsing loop, forcing the pipeline to process a maximum of 4 requests per minute, keeping it safely under the radar. *(Future optimization: Implement prompt batching).*

### Challenge 3: The Data Mismatch Rejection
> [!bug] Issue
> The newly deterministic `AlignmentValidator` rejected a highly qualified "Architect" (Score 5) applying for a "Principal" role. Why? The upstream `JDAnalyzer` incorrectly labeled the Principal role with the string `"mid"`, causing a fatal math calculation (`|5 - 2| = 3 gap`).

**The Fix:** We updated the `compare_seniority_levels` tool to prioritize the numerical `level_score` (which correctly extracted as 5) over the flawed string label. We updated the tool signature to accept `jd_score_override=jd_level_score`, instantly unblocking the pipeline.

## 📈 The Results
* **Token Reduction:** Dropped anticipated token consumption from ~98,500 down to **~12,500 - 23,500 tokens per run** (a >75% reduction).
* **Reliability:** The pipeline is now immune to LLM hallucinations during the strict alignment validation phase.
* **Speed:** Eliminated 3 to 4 unnecessary LLM API calls per run by relying on standard Python state lookups and deterministic `difflib` comparisons instead of AI summaries.
