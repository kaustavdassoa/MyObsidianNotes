# 📝 The 5-Pattern Instruction Framework (Prompt Engineering)

The **5-Pattern Instruction** framework is a prompt engineering standard designed to transition LLMs from conversational chatbots into deterministic, reliable software components. 

When building with the Google Agent Development Kit (ADK), this framework acts as the definitive "API contract" for your agent's reasoning engine, dictating exactly how it interacts with tools, states, and output schemas.

---

## 1. Identity (The Role & Context)
> [!info] Definition
> Defines the exact persona, expertise level, and operational context of the agent.

**ADK Refinement:** Leverage **State Templating** (`{var?default}`) to dynamically inject context without hardcoding it, making the agent reusable across different sessions.

* ❌ **Standard:** "You are an anti-money laundering auditor."
* ✅ **ADK Optimized:** "You are a Level 3 Anti-Money Laundering (AML) Auditor operating under the regulatory jurisdiction of `{app:compliance_region?Global}` for the `{user:client_type?Retail}` banking sector."

## 2. Mission (The Objective & Output)
> [!info] Definition
> The singular, primary goal of the agent for a given invocation.

**ADK Refinement:** The Mission must directly align with the Pydantic `output_schema` defined in your Python code. If the agent is an `AgentTool` (sub-agent), it defines exactly what the Orchestrator expects back.

* ❌ **Standard:** "Review this transaction and tell me if it looks suspicious."
* ✅ **ADK Optimized:** "Your mission is to analyze the provided transaction log and generate a strict compliance risk assessment. You must structure your final findings to perfectly match the `AML_Risk_Report` JSON schema."

## 3. Methodology (The Tool Execution Logic)
> [!important] The Most Critical Section for ADK
> The step-by-step logical sequence the agent must follow. This explicitly dictates **when** and **in what order** to invoke the tools configured in your `tools=[...]` array to prevent LLM confusion.

* ❌ **Standard:** "Look up the client's history and calculate their risk."
* ✅ **ADK Optimized:** "Follow this exact sequence:
  1. **Data Gathering:** Invoke the `get_kyc_record` tool using the provided Account ID.
  2. **External Verification:** If the record is older than 6 months, invoke `Google Search` to check for recent negative news.
  3. **Calculation:** Pass the transaction volume to `calculate_risk_score`. Do not attempt to calculate this mathematically yourself."

## 4. Boundaries (The Guardrails)
> [!warning] Definition
> Strict negative constraints that dictate what the agent must *not* do. Used to prevent "tool hallucination" and manage error states.

* ❌ **Standard:** "Don't make things up."
* ✅ **ADK Optimized:** "- **Tool Adherence:** Never invent a risk score. If `calculate_risk_score` fails, return 'INCOMPLETE_AUDIT'.
  - **Scope:** Do not provide investment advice or interact with tools outside your methodology.
  - **Memory:** Only use data from the `{temp:current_transaction}` namespace; ignore previous session history."

## 5. Few-Shot Examples (The Pattern Matching)
> [!info] Definition
> Input/output pairs showing the model exactly what "good" looks like.

**ADK Refinement:** Because the ADK handles tool calling under the hood, few-shot examples should demonstrate the expected *reasoning trace* alongside the final output format.

* ✅ **ADK Optimized:**
  **Example 1: High Risk Flag**
  *Input:* Transaction of $50,000 from Account A to offshore Account B.
  *Expected Thought Process:* I need to call `get_kyc_record` for Account A. The record shows low income. I will flag this.
  *Final Output:* `{"status": "FLAGGED", "reason": "Transaction volume exceeds 10x historical average."}`

## 🛠️ Implementation Example (ADK YAML Manifest)

```yaml
# aml_auditor_agent.yaml
name: aml_auditor_agent
model: gemini-2.5-pro
description: Specialized sub-agent for executing targeted AML transaction audits.
instruction: |
  # IDENTITY
  You are a Level 3 Anti-Money Laundering (AML) Auditor operating under the regulatory jurisdiction of {app:compliance_region?Global}.

  # MISSION
  Analyze the provided transaction log and generate a compliance risk assessment formatted strictly to the expected output schema.

  # METHODOLOGY
  1. Invoke the `get_kyc_record` tool to retrieve the client's baseline profile.
  2. Pass the transaction amount and baseline profile to the `calculate_risk_score` tool.
  3. Synthesize the tool responses into your final report.

  # BOUNDARIES
  - NEVER estimate mathematical risk scores; always rely on the calculation tool.
  - If the `get_kyc_record` tool returns a 'Not Found' error, halt the audit and return "MANUAL_REVIEW_REQUIRED".
  - Do not reference data outside of the current {temp:transaction_id}.

  # FEW-SHOT EXAMPLES
  Input: Validate TXN-9982
  Output: {"audit_status": "CLEARED", "risk_tier": "LOW", "auditor_notes": "Matched baseline profile via KYC tool."}
```
